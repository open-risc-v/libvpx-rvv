# libvpx G3 第一个内核：SAD（2026-11-15）

libvpx 的 SSE/NEON 内核有 190+ 文件，全量照搬不现实。先挑**语义最简单、收益可量**的
SAD（逐像素绝对差之和）做第一个 RVV 内核，把"写-验-测"的闭环先跑通。

## 实现

`src/vpx_dsp/riscv/sad_rvv.c`：8x8 / 16x16 / 32x32 / 64x64 四档，语义与上游
`vpx_dsp/sad.c` 的 `static sad()` 完全一致。

关键点：**u8 上不能直接做 `abs(a-b)`**（会回绕）。用

```
hi = vmaxu(a,b); lo = vminu(a,b); d = hi - lo;      // d ∈ [0,255]
total += vwredsumu(d)                                // u8 宽度归约到 u16
```

单行最多 `width*255`（64 宽 = 16320），u16 归约不会溢出；跨行累加到 u32。

## 两个 GCC intrinsic 坑

1. `__riscv_vwredsumu_vs_u8m1_u16` 不存在，正确名是 `..._u8m1_u16m1`；
2. `vwredsumu` 在 GCC 14 的 1.0 intrinsic 里**返回的是 u16m1 向量**（结果在元素 0），
   不是标量，必须再 `__riscv_vmv_x_s_u16m1_u16` 取出来，否则报
   `cannot convert a vector of type 'vuint16m1_t' to type 'unsigned int'`。

## 验证

`test/kernel_sad.c` 里的 C 参照逐字拷贝自上游 `sad()`。两侧同一份文件，
唯一差别 `-DUSE_RVV=1/0`，均 `-O3 -march=rv64gcv -static`，RVV 侧多链一个 `sad_rvv.c`。
RVV 侧同时算 C 与 RVV 并逐值比对（qemu 下四档全部一致）。

## 真机结果（SpacemiT K3，三轮迭代）

同一台板、同一 `bench_c` 参照，只换 RVV 内核版本：

| 尺寸 | C ns/call | v1 每行归约 | v2 16B chunk | v3 32B chunk | **v4 混合分派** |
|---|---|---|---|---|---|
| 8x8 | 70.7 | 96.4（0.73×） | 58.9（1.20×） | 65.9（1.07×） | **58.2（1.21×）** |
| 16x16 | 236.3 | 251.4（0.94×） | 109.3（2.16×） | 121.7（1.94×） | **108.4（2.18×）** |
| 32x32 | 998.7 | 998.6（1.00×） | 410.7（2.43×） | 233.5（4.28×） | **233.5（4.28×）** |
| 64x64 | 3195.3 | 3196.2（1.00×） | 1634.7（1.96×） | 911.2（3.51×） | **903.3（3.54×）** |

（v1 的 16x16/32x32/64x64 C 参照取的是同一轮 a8x8 记录，重跑后 C 侧略有浮动，
比值以同轮为准。）

### 三条结论

1. **每行归约是主要瓶颈**。v1 在 8x8 只有 0.73×，把归约挪到块末尾（v2）立刻变 1.20×；
   32x32 从 1.00× 到 2.43×。
2. **chunk 宽度要按块大小分派**。VLEN=256 时：
   - 宽 ≤ 16 用 u16m1 累加器（chunk 16 字节）：8x8 1.21×、16x16 2.18×；
   - 宽 ≥ 32 用 u16m2 累加器（chunk 32 字节）：32x32 4.28×、64x64 3.54×。
   v3 统一用 32 字节在 16x16 上反而退化（1.94×），所以最终按宽度分两条路径。
3. **8x8 只能做到 1.2×**，这是 64 个像素的算术量摆在那儿 —— 单次调用的固定开销
   （函数调用 + vsetvl + 尾部归约）已经占了相当比例。要再往上只能做"多块批处理"
   （一次调用算多个 8x8），但那就不是 SAD 的接口了。



## 一个被 qemu 抓出来的真 bug

混合分派的第一版假设 "width ≤ MVL"，`vsetvl_e16m1(width)` 直接用整行长度。
在板上（VLEN=256，MVL=16）16x16 是对的，**但 qemu 默认 VLEN=128 时 MVL 只有 8**，
16 宽只处理了一半，`sad16x16` 直接算出 `c=22340 rvv=11170`（正好一半）。

教训：**不要假设 VLEN/MVL**。即便目标板固定 256，qemu 校验和未来换板都会踩到；
小块路径也必须按 chunk 循环、用 `vsetvlmax` 取上限。
